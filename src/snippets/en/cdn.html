What a CDN edge node is

A CDN (content delivery network) keeps copies of site content in data centers around the world. When you visit a site on a CDN, your request does not travel all the way to the origin server; it lands in one of the CDN's edge data centers (PoPs), which serves the cached content locally. That data center is your edge node. CDNs usually name it after the IATA code of a nearby airport: HKG is Hong Kong, NRT is Tokyo Narita, LAX is Los Angeles, FRA is Frankfurt.

CDNs assign you to a node in one of two ways. Anycast: the same IP is announced from every data center at once, and internet routing decides where you land. Cloudflare and Google Cloud global load balancing work this way, and the result mainly depends on where your exit is and how your ISP connects. DNS routing: when resolving a domain, the CDN returns a data center address based on the location of the DNS server that queried on your behalf. Most CDNs, such as CloudFront and Akamai, rely on this, so which DNS you use and where it is directly changes the node you hit. One person landing on different continents with different CDNs is not unusual.

What this check does

  1. For each CDN on the list, send one cross-origin request to its public test file (no cookies, no referrer) and read the response header that carries node information. For Cloudflare it reads colo from the /cdn-cgi/trace body; for Google Cloud it reads the returned region name.
  2. Once the connection is open, request again and record that time as latency. The first request includes DNS resolution and the TCP and TLS handshakes, which do not reflect everyday speed.
  3. If the CDN refuses the cross-origin read, retry with an opaque latency-only request to tell "connects but can't be read" from "does not connect at all".
  4. Convert node codes to cities, then ask this site for the approximate coordinates and country of "the IP this site sees" (the same data as on the home page) and compute the distance to each node, classified by the rules under "Reading the results". No CDN tells a web page where you are, so this location refers to the address this site sees. The Cloudflare row's trace reports the exit IP Cloudflare sees; if it is not the same exit this site sees (common with split-routing proxies), these coordinates do not apply, and this page judges nearness only by the country/region Cloudflare reports, without distance. For "the country/region of the exit" in the rules, the one in Cloudflare's trace is used when available, the same approach as the Cloudflare edge check, so a node gets the same verdict on both pages; if it disagrees with this site's records, a note appears under "You are hitting". The country from this site's records is only used when the trace could not be read.

6 at a time throughout, up to 6 seconds per request; one CDN takes at most three back-to-back steps ("read node, read body, measure latency again"), capped at about 16 seconds. All 19 usually finish within 10–20 seconds. Probe requests go straight from your browser to each CDN; this site's server is not involved and receives no results. The only request sent back to this site is the approximate-location lookup, which carries no probe data.

Reading the results

  • Nearby / In region / Cross-region: the node was read and nearness could be judged; the tiers are exactly the same as on the Cloudflare edge check. Within 1000 km, or a node near your exit (for example Hong Kong, Taipei, Tokyo, Osaka, Seoul or Singapore for visitors in mainland China), or in the same country/region as the exit and within 3000 km, counts as nearby. Anything else within 3000 km, or in the same country/region as the exit (including thousands of kilometers inside large countries such as the US, Russia or Brazil), counts as in region. The rest is cross-region. Most CDNs nearby is ideal; one or two in region is common; several cross-region at once means your exit or DNS does not look close to you from the CDN's point of view.
  • Identified / Read: the node was read but nearness could not be judged; the neutral gray label means neither good nor bad. Identified means the city or country was recognized but distance could not be computed (your location is missing, does not apply to this exit, or the CDN only gives a country), and the node is not in your country/region or nearby; nodes in the same country or nearby count as nearby even without a distance. Read means only a node ID or node IP was available. Formats that cannot be parsed are shown as is and never guessed as a city.
  • Reachable · node info not exposed: the request succeeded, but this CDN does not expose the node header to other sites, so only latency is shown.
  • Reachable, cross-origin reads not allowed: the CDN does not accept cross-origin reads at all; latency was measured with an opaque request.
  • Unreachable: timed out or failed to connect. Your network may not reach this CDN, or the test file itself may be gone; a single unreachable CDN is nothing to worry about.

Why some CDNs only show latency

This follows from browser security rules, not a failed check. When a page makes a request to another site, scripts can only read a few "safe" response headers by default (content type, length, cache policy and the like); the x-served-by, x-amz-cf-pop and via headers that CDNs use to mark nodes are not among them, and other sites can only read them if the CDN lists them in Access-Control-Expose-Headers. Developer-facing public CDNs such as jsDelivr expose them all; many test files don't. For CDNs that don't, this page only reports latency and never makes up a node; to see their nodes, look at the response headers of these requests in the Network panel of your browser's developer tools.

The Cloudflare row only shows the data center you hit. Its different networks (Free, Enterprise, China network, 1.1.1.1) route the same person to different nodes; for the full comparison, exit IP, HTTP/3 and WARP status see the Cloudflare edge check; if nodes are generally far away and you suspect DNS, check who resolves names for you with the DNS leak test.

FAQ

Why do some CDNs show latency but no node?
Browser cross-origin rules only let a page read response headers that the other site explicitly exposes. CDNs put node codes in custom headers such as x-served-by, x-amz-cf-pop and via, and scripts on other sites can only read them if the CDN lists them in Access-Control-Expose-Headers. For CDNs that don't, this page can only confirm that they connect and how long it takes, not the node. This is not a problem with your network; any web-based tool has the same limit.
The node I hit is far away. What's wrong?
There are three common causes. First, the exit IP's registered location does not match where you are: you use a proxy or VPN, or the IP database places the range elsewhere, and the CDN only sees the exit. Second, DNS routing: most CDNs, such as CloudFront and Akamai, assign nodes by the location of the DNS server that resolves for you, so if you use a public resolver abroad or DNS goes through a proxy, the node follows the DNS. Third, ISP interconnection: from mainland China, ISPs often lack good interconnection with foreign CDNs, so you get routed to the US West Coast. Start by checking who resolves names for you with the DNS leak test.
Is it normal for the same CDN to give a different node each time?
Yes. CDNs adjust routing constantly based on data center load and link quality, anycast routes change, and DNS routing results also depend on cache lifetimes. Switching between neighboring cities (Hong Kong and Tokyo, Frankfurt and Amsterdam) is nothing to worry about; frequent jumps to another continent are worth investigating.
With a proxy on, CDNs land in different cities. Which one counts?
The one used by the site you want to visit. CDNs see your exit and your DNS: with a global proxy, every CDN should land near the proxy exit; with rule-based routing, different CDN domains may go direct or through different proxy nodes, so the cities naturally differ, which is a useful way to check that your routing rules work as intended. To see the exit IP site by site, use the split routing test.
Does this site record the results?
No. Probe requests go straight from your browser to each CDN's public test file, without cookies or a referrer, and this site's server receives no probe data. The nodes and latency shown exist only on this page and disappear when you close it. The approximate location used for distance comes from asking this site for "the IP this site sees", the same lookup as on the home page, and the request carries no check results.

What a DNS leak is

The first step in opening a URL is resolving the domain: the device asks a DNS server which IP the domain maps to, and only then can it connect. This is done by a recursive resolver, usually the one your ISP assigns automatically, or one you set by hand such as 8.8.8.8, 1.1.1.1 or 223.5.5.5. It queries the root, the TLD and the authoritative servers in turn and returns the result to you.

This step is independent of whether web traffic goes through the proxy. Browser-extension proxies only take over HTTP(S) requests, and so do some VPN clients that change routes but not the DNS settings. The result: websites see the proxy exit, while your ISP sees every domain you looked up. That is a DNS leak.

In some cases a DNS leak reveals more than an IP leak: the IP says where you are, the domain log says what you visit. Seeing it requires no decryption, and HTTPS does not hide it: HTTPS encrypts the connection, not the domains you looked up.

What this check does

  1. The browser generates 8 distinct one-time random subdomains of the form {32 random characters}.edns.ip-api.com.
  2. It requests them over HTTPS at the same time. These names have never existed, so no cache has them, and your recursive resolver has to ask ip-api.com's authoritative server for each one.
  3. ip-api.com's authoritative server records the address that asked and returns it to the browser in the response to that request.
  4. The page sends the collected resolver addresses to this site to add country/region, ISP and ASN, then compares them with your HTTP exit and draws a conclusion.

Why 8 and not 1: a public DNS service runs many recursive machines, and which one sends a given query is random. One lookup shows only one of them; several show the range. Each subdomain is used once, which also avoids caches: a cache hit at any layer would make the test useless.

Reading the results

  • Resolver and exit share an ASN: DNS and web traffic take the same path. Either you use no proxy, or the proxy also handles DNS. This is the cleanest case.
  • Resolver is a well-known public DNS in the same country/region as the exit: no cross-border leak, but that provider gets your domain log. Whether that is acceptable depends on whether you trust it.
  • Resolver is your local ISP, but the exit is elsewhere: a typical DNS leak. The proxy only handles web traffic, and DNS lookups still go through your local network.
  • No resolver captured: the requests did not reach ip-api.com. Common causes are network restrictions or a browser extension blocking them. This does not mean you are safe, only that this run measured nothing; try another network.

If the result shows ECS, the resolver told the authoritative server your subnet (EDNS Client Subnet, RFC 7871). This lets CDNs route you to a nearby node, at the cost that every authoritative server learns roughly which subnet you are on, even when DNS itself does not cross a border.

How to prevent DNS leaks

  • Let the VPN client handle DNS. This is the most complete fix. In WireGuard, set DNS = in the config; in OpenVPN on Windows, use block-outside-dns; commercial clients usually have a "Block DNS leaks" switch. Clients in TUN mode that take over the whole network stack don't have this problem.
  • Enable DoH / DoT. Browsers and operating systems can encrypt lookups and send them to a chosen provider. This changes who resolves and whether the path can be observed; it does not mean nobody knows what you visit.
  • Check the DNS settings on your system and router. Many leaks come from ISP DNS hard-coded on the router, which DHCP pushes back to your devices no matter what you change on them.
  • Disable IPv6, or make sure IPv6 also goes through the tunnel. With a proxy that only handles IPv4 on a dual-stack network, DNS leaks out over IPv6 untouched. This one is the hardest to notice.

After making changes, come back and test again. Each run uses new random subdomains, so nothing from the last run is cached.

FAQ

I'm on a VPN. Why does DNS still go to my ISP?
Because resolution happens before the connection. The system has to turn the domain into an IP before it knows where to send packets, and which DNS it uses is set by the network adapter configuration. Browser-extension proxies that only handle HTTP(S), and some VPN clients that change routes but not DNS, leave that configuration alone. So websites see the proxy exit, while your ISP gets every domain you visit.
The address shown doesn't match the 8.8.8.8 I set. Is the test wrong?
No. This is the most commonly misread part of the test. 8.8.8.8 is where you send queries; the authoritative server sees the address of the machine in Google's recursive cluster that actually sent the query, usually in 74.125.x or 172.253.x. Both belong to the same company and ASN, but they are never the same address. That is why this page identifies providers by ASN rather than IP.
Why does one test show several resolvers?
A public DNS service runs many recursive machines, and which one sends a query is random; many systems also have a primary and a secondary DNS configured. This page sends several distinct random subdomains to show that range, and every one of those machines saw the domains you visit.
With encrypted DNS (DoH / DoT) on, do I still need to test?
Yes, and the result may not be what you expect. Encryption stops others on the path from seeing queries; it does not change who does the lookup in the end. DoH replaces plain-text queries with HTTPS requests to one provider, and that provider still knows what you visit. That is what this page tests: who finally asks the authoritative server on your behalf.
Does this site store DNS test results?
No. The random subdomains are resolved by ip-api.com's public EDNS service, which sees your resolver addresses, ECS subnet and IP, and handles them under its own policy. The page then sends the resolver addresses and your exit IP to this site to look up their owners. This site does not record the test; owner lookups are cached briefly per IP and not linked to the test.

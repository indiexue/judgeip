What a Cloudflare node is

Cloudflare runs data centers in more than three hundred cities, and every site on Cloudflare shares this network. When you visit such a site, your request does not go straight to the origin server; it lands in one of Cloudflare's edge data centers first, which handles the TLS handshake, caching and security filtering, then decides whether to contact the origin. That data center is the node (Cloudflare calls it a colo), named after the IATA code of a nearby airport: HKG is Hong Kong, NRT is Tokyo Narita, LAX is Los Angeles, FRA is Frankfurt.

Cloudflare uses anycast to announce the same IP from every data center, so internet routing decides where you land. Ideally that is the nearest one, but your ISP's international links, its interconnection with Cloudflare and the target site's plan can all change the result, which is why one person can see latency differences of hundreds of milliseconds across sites.

Every site on Cloudflare has a public diagnostic path, /cdn-cgi/trace, that reports in a few lines of plain text: the data center you hit (colo), the exit IP it sees (ip) and its country (loc), HTTP and TLS versions, whether SNI is encrypted, the key exchange algorithm, and whether WARP or a Zero Trust gateway is in use. Every conclusion on this page comes from those lines.

What this check does

  1. Request speed.cloudflare.com/cdn-cgi/trace twice: the first only opens the connection, and the second result is shown. The local clock is read before and after the second request, and the midpoint is compared with the edge time to get the clock offset (edge time is only accurate to the second, so the offset is reported in whole seconds).
  2. Ask this site for the details of "the IP this site sees": ISP (ASN), city and approximate coordinates, the same data as on the home page. The trace has no coordinates, so this location is only used to compute the distance to the node when it is the same exit Cloudflare saw in the previous step (same IPv4, or the same /64 for IPv6); otherwise distance is judged by country only.
  3. Request https://1.1.1.1/cdn-cgi/trace: an IP literal can only use IPv4, so it shows your IPv4 exit and where you land on the 1.1.1.1 network.
  4. For each of the 7 Cloudflare networks of different tiers in the table below, send 1 warm-up and 3 requests in a row, and use the fastest as the latency, recording the node and protocol hit. At most 4 networks are tested at once to avoid competing for bandwidth.
  5. Load Cloudflare Turnstile from challenges.cloudflare.com and run one bot check each with the non-interactive and managed widgets; the token is passed to this site's server, which verifies it with Cloudflare once (see below).

Requests to Cloudflare (steps 1, 3 and 4) carry no cookies, no referrer and no custom headers (custom headers would trigger a CORS preflight, which the trace path does not answer). Results stay on this page and are not sent back to this site. Step 2 is a request to this site itself and carries no check results; all this site learns from it is your IP, the same as when you opened the page. The Turnstile token only counts once the server verifies it. This site's server discards the token and result after verifying, and only keeps a verification count per IP that expires after 1 hour, for rate limiting.

Reading the results

  • Node and distance: within 1000 km, or a node near your exit (for visitors in mainland China: Hong Kong, Taipei, Tokyo, Osaka, Seoul, Singapore, the closest landing points available outside China), or in the same country/region as the exit and within 3000 km, counts as nearby. Anything else within 3000 km, or in the same country/region as the exit (in large countries such as the US, Russia or Brazil, thousands of kilometers inside the country is not another region), counts as in region. The rest is cross-region, with noticeably higher latency. Without your coordinates, nodes in the same country or nearby still count as nearby, and the rest are only marked a neutral "identified". Distance is estimated from the approximate coordinates of the exit IP this site looked up and is only an order-of-magnitude reference; if Cloudflare's exit differs from the one this site sees, those coordinates do not apply and no distance is estimated.
  • Exit IP: if it matches the same-family address this site sees, Cloudflare and this site are reached through the same exit; same family but different means split routing or a multi-exit proxy; one IPv4 and one IPv6 is just a dual-stack network using different paths, which is normal.
  • HTTP/3: the first visit is usually HTTP/2; the browser switches to QUIC only after it learns the site supports HTTP/3, so refresh and test again. HTTP/1.1 often means a proxy in the middle that does not support newer protocols.
  • TLS, ECH and post-quantum: TLS 1.3 is the current standard. SNI shown as "encrypted (ECH)" means even network devices along the way cannot see the domain you visit. MLKEM or Kyber in the key exchange means the connection uses a hybrid post-quantum key exchange.
  • WARP / Zero Trust gateway / remote browser isolation: if any is on, Cloudflare no longer sees your direct exit, so read the node and exit IP as those of WARP or your company gateway.
  • Clock offset: the edge time in the trace is only accurate to the second, so the offset is estimated in whole seconds; an estimate of 3 seconds or more (a real offset of at least about 2 seconds) is flagged. A wrong clock can break TLS certificate checks, two-factor codes and more.

Why different networks hit different nodes

A site's Cloudflare plan decides which data centers and routes it can use. Enterprise sites can use every node and better routing; the China network (in partnership with JD Cloud) only routes to nodes inside China for visitors in mainland China; 1.1.1.1 DNS and WARP use a separate anycast range; the speed test site and cdnjs each have their own routing. So it is common for rows in the comparison to hit different nodes. If they all land on the same nearby node, your network's route to Cloudflare is excellent.

There is no "Free" row in the comparison: this site is not on Cloudflare, and there is no third-party site that can be relied on to stay on the Free plan. If you have a Free-plan site yourself, open its /cdn-cgi/trace in your browser and compare the colo= line.

What the Turnstile check tests

Turnstile is Cloudflare's replacement for traditional CAPTCHAs. It reads the browser environment in the background, runs a short challenge, and combines that with what Cloudflare knows about the IP and network to decide whether the visitor is human. More and more sites use it to keep bots away from sign-in, sign-up, comments and downloads. If your browser keeps failing it or always has to click, those sites become tedious to use.

This page runs one check with each of two widget modes to see whether your browser passes automatically without doing anything:

  • Non-interactive mode: the widget only shows progress and never offers a checkbox. If Cloudflare is satisfied it issues a token, otherwise it fails, so it answers most directly whether you pass invisibly.
  • Managed mode: Cloudflare decides whether to ask you to click. Most normal browsers pass automatically; when signals are not clean enough, a "Verify you are human" checkbox appears and you have to click it. The manual IP lookup on this site's home page uses this mode.

"Response time" on the card is the time from the start of verification to receiving the token, including any wait before you click. The page then passes the token to this site's server, which verifies it together with your IP against Cloudflare's siteverify endpoint: whether the token is valid, used for the first time, and issued for this card on this site (hostname and action must match). Only a token received in the page and confirmed by the server counts as a pass. "Response metadata" lists the fields Cloudflare returned during verification (filtered and length-limited by this site); cData is compared by the page with a random value generated for this render, and only marked as matching or not for you to check, not counted in the verdict.

Managed mode passed without asking you to click

To Cloudflare, this browser and network look like an ordinary visitor: the exit IP has a normal reputation, the browser's characteristics are consistent, and there are no obvious signs of automation. This is the best outcome; you probably won't see a challenge on other sites that use Turnstile either.

Asked to click, or non-interactive mode failed

This only means Cloudflare could not decide automatically that you are human; it is not a block. Common causes: the exit is a data center, VPN or proxy address (lots of automated traffic on the same exit lowers its reputation); privacy extensions or anti-fingerprinting browsers alter or block browser characteristics; the browser shows automation traits (for example controlled by Selenium or Playwright); the local clock is far off; or the network is too slow for the challenge to finish in time. Switch exits or temporarily disable the relevant extensions, click "Reset" and test again to find out which one it is. Cloudflare decides only from the signals it can see; this page reports the result as is but cannot tell you which signal mattered.

If the card shows "script failed to load", the browser could not load Turnstile from challenges.cloudflare.com: your network blocks the domain, or an extension or proxy rule blocked it. In that case every site that uses Turnstile will get stuck at verification. "Not loaded after a long time" means the script was not ready within 15 seconds: it may be blocked, or the network to challenges.cloudflare.com may just be slow; if the script arrives later, the card starts automatically. Errors marked on the card as a deployment issue on this site (for example 110200: the current domain is not in the widget's allowed list) are caused by this site's configuration, not your browser.

FAQ

I am in China or elsewhere in Asia. Why do I hit a US node?
Cloudflare routes by network, not by map: the data center you land in depends on your ISP's international links, Cloudflare's interconnection with that ISP, and the target site's plan. Visitors in mainland China reaching sites not on the China network are often routed to US West Coast data centers such as Los Angeles (LAX) or San Jose (SJC), while Enterprise sites more often land in Hong Kong, Tokyo or Singapore. This is routing policy, not a fault in your network.
Why is the exit IP Cloudflare sees different from the one this site sees?
First check whether both addresses are the same family. One IPv4 and one IPv6 is normal: on a dual-stack network the browser may pick different families for this site and for Cloudflare, and both are your own exits. If both are IPv4 (or both IPv6) and still differ, traffic to Cloudflare uses a different exit, which is common with per-domain proxy rules or proxy services with multiple exits.
Why HTTP/2 instead of HTTP/3?
The browser has to receive an Alt-Svc header over an HTTP/2 connection first to learn that the site supports HTTP/3; only new connections after that use QUIC. So the first visit is usually HTTP/2, and switching to HTTP/3 after a few refreshes is normal. If it stays on HTTP/2, your network probably blocks UDP 443, or your proxy does not forward QUIC. This does not affect normal browsing.
What are WARP, Zero Trust gateway and remote browser isolation?
WARP is Cloudflare's client for faster, encrypted connections; with it on, sites see WARP's exit, and plus means WARP+ (the paid Argo route). Zero Trust gateway means your traffic passes through a Cloudflare security gateway configured by some organization, common on company devices. Remote browser isolation (RBI) means the page actually runs in a Cloudflare remote browser and you only see the rendered result. If all three show off, you connect to Cloudflare directly.
The Turnstile test asked me to click. Is something wrong with my network?
Not necessarily. Managed mode lets Cloudflare decide from browser and network signals whether to ask for a click. Most normal browsers pass directly, but the chance of being asked rises clearly with a data center, VPN or proxy exit, privacy extensions that alter browser characteristics, automation traits, or a wrong local clock. Passing after one click only means you did not pass invisibly; it is not a block. Non-interactive mode never shows a checkbox and simply fails when Cloudflare is not satisfied, so it is the better indicator of whether you pass automatically.
Does this site record the results?
No. Node check requests go straight from your browser to Cloudflare's sites, without cookies or a referrer; the trace content and node results are shown only on this page, never sent back to this site, and disappear when you close the page. The approximate location used for node distance comes from asking this site for "the IP this site sees", the same lookup as on the home page, and the request carries no check results. The one-time Turnstile token is passed to this site's server, verified once with Cloudflare together with your IP, then discarded; this site only keeps a per-IP verification count that expires automatically after 1 hour, for rate limiting.

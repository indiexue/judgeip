What a WebRTC leak is

WebRTC (Web Real-Time Communication) is the browser's built-in support for real-time audio, video and peer-to-peer data, used by most web-based video meetings, screen sharing, live chat and cloud gaming. Peer-to-peer connections first have to solve one problem: both devices sit behind NAT and don't know each other's public address. WebRTC solves it with ICE: the browser sends a request to a STUN server, which replies with the address and port it saw the request come from. That result is called an srflx (server reflexive) candidate.

The catch: ICE gathers addresses over UDP, sent directly by the operating system's network stack, bypassing the browser's HTTP proxy settings. So while web traffic goes through the VPN or proxy and websites see the proxy exit, JavaScript on the same page can start ICE gathering and get the real public address of your home connection. That is a WebRTC leak.

It's not only the public address. ICE also gathers host candidates, the local addresses on your network adapter (192.168.x.x, 10.x.x.x and so on), which reveal your LAN's subnet. Since around 2019, Chrome, Edge and Firefox replace real local addresses with mDNS host names by default (like a1b2c3d4-….local), which reduces that risk a lot, but the public-address path is still open.

What this check does

  1. For each STUN server on the list, create a separate RTCPeerConnection with only that server as the ICE server.
  2. Create a data channel and generate an offer, which makes the browser start gathering ICE candidates.
  3. Read each gathered candidate and sort by type: srflx / relay are public addresses, host is a local address.
  4. Fetch IPv4 and IPv6 HTTP exits and compare only addresses in the same family, grouping IPv6 privacy addresses by /64. Without a same-family HTTP address, the result remains uncomparable.

Why test servers one at a time instead of putting them all in iceServers: together, the browser only returns deduplicated candidates, so you can't tell which server answered and which never connected. Testing separately shows cases like "STUN in China works, everything abroad times out", which is also why the list has servers both in and outside China. One server timing out doesn't mean you are safe, only that it didn't connect.

Reading the results

  • No public address found: no public candidate was obtained this time. Network restrictions, browser policy or an unavailable STUN service may explain it; this does not guarantee safety.
  • Matches a known same-family HTTP exit: no additional exit was observed. IPv6 uses /64 grouping; this does not prove that all UDP traffic uses a proxy.
  • Differs from a same-family HTTP exit: multiple exits, split routing or proxy settings may explain the difference. Check the actual route before calling it a leak.
  • No same-family address to compare: for example, HTTP IPv6 and STUN IPv4 alone cannot be labelled a match or a leak.
  • Local address starting with 192.168 / 10.x found: your browser doesn't use mDNS masking, so your LAN subnet is exposed.

How to prevent WebRTC leaks

The most direct fix is an extension that restricts WebRTC address gathering in the browser. Both of these are in the Chrome Web Store; after installing, reload this page and test again to confirm:

  • WebRTC Network Limiter Published by Google. It changes Chrome's WebRTC policy to use only the path your proxy takes, so video calls keep working without exposing your real address.
  • WebRTC Protect — Protect IP Leak A one-click blocking extension that disables WebRTC address gathering outright. Good for people who never use audio or video calls in the browser.

Besides extensions, there are a few other options: in Firefox, set media.peerconnection.enabled to false in about:config, at the cost of losing web-based audio and video calls entirely; use a VPN client with a global TUN / TAP mode so UDP also goes through the tunnel, which removes this path at the root; or block port 3478, commonly used by STUN, on your router. Note: disabling WebRTC breaks services such as Google Meet, the Tencent Meeting web app and the Discord web app. If you use them regularly, prefer a policy-limiting option like Network Limiter over turning WebRTC off.

FAQ

I use a VPN. How can my real IP still show up?
Most browser-extension proxies and SOCKS / HTTP proxies only take over HTTP(S) traffic over TCP. WebRTC's ICE gathering uses UDP, sent straight from the physical adapter, bypassing the proxy settings. This isn't a VPN bug but a result of how the layers work, unless the VPN runs in TUN mode and takes over the whole network stack.
Every server timed out. Does that mean I'm safe?
Not necessarily. A timeout only means those STUN servers can't be reached right now (network restrictions, server failure, UDP blocked). On another network or with another server, the result may be completely different. Even when candidates match a same-family HTTP exit, that only means no additional exit was observed in this test; it does not guarantee that all traffic is safe.
What does a local address shown as a .local string mean?
This is mDNS masking: the browser replaced the real local address with a random host name. It is expected and means your browser version has this protection.
Does this site store WebRTC test results?
No. The whole test runs in your browser, and candidate addresses are never sent back to this site's server. The addresses on the page exist only in this tab and disappear when you close it.
